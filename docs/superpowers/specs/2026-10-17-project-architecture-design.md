# 项目分层与模块化改造设计

## 1. 目标与约束

本项目是一款本机运行的集装箱业务网页工具。用户双击 `ContainerPlanner.exe` 后，由程序启动本地服务并打开浏览器网页；用户不需要在使用电脑上安装编程环境。网页是应用载体和统一入口，业务功能以并列模块形式提供。

项目规划要达到以下目标：

- 保留便携启动方式、浏览器操作方式和本机处理资料的工作方式。
- 将集装箱装箱计算作为独立功能模块。
- 新增单据自动处理模块：导入合同、PI 等资料，提取和核对业务数据，按用户提供的模板生成 INV、PL 等文件。
- 明确应用载体、功能模块和共享接口的责任边界，使单个模块可以独立理解、修改和验证。
- 通过分层 `AGENTS.md`、README、接口文档和项目管理约定，让后续参与者按需读取规则。

## 2. 现状与迁移约束

当前项目根目录包含 `ContainerPlanner-网页版/`、发布包、真实业务资料、测试数据、测试记录和测试工具。网页资源及 Python 运行组件位于已打包程序的 `_internal` 目录中，根目录没有独立的应用源码、集装箱功能源码或可复现的构建脚本。

因此，本设计分两类工作：

1. **文档和结构先行**：建立项目总览、分层规则、模块目录约定、接口契约和样例位置。
2. **源码确认后迁移**：盘点和恢复可维护源码，确认打包及启动流程，再把现有网页和装箱逻辑纳入独立模块。不能把打包产物直接视为完整、可复现的源码。

现有真实业务资料保持原位，不自动复制到模块样例或发布包。单据模块的可分发样例应使用用户提供并确认可用于样例的文件，优先制作脱敏副本。

## 4. 组件责任和依赖方向

### 网页应用载体

负责程序启动、本地网页服务、全局导航、模块装配、静态资源入口和共享的文件选择/下载能力。载体不实现装箱算法、单据识别规则或单据模板映射。

### 集装箱模块

负责集装箱尺寸、货物清单、装箱模式、摆放计算、3D 结果展示和装箱方案导入导出。其内部算法和页面由本模块维护，通过公开接口接收货物与柜型数据、返回计算结果。

### 单据模块

负责读取 Excel、Word、PDF 输入，提取字段并保留来源与可信度，供用户核对；按已确认的数据映射和用户模板生成 Excel、Word 或 PDF 文件。未知或不确定字段需要显式呈现，不得悄悄猜测并写入最终单据。

### 共享层

只收纳被至少两个模块实际使用且语义稳定的契约或通用能力。某个模块的领域逻辑不得为了方便被放进 `shared/`。

### 依赖规则

- 网页载体可以调用功能模块公开接口；功能模块不得依赖另一个模块的内部文件。
- 模块间协作通过 `shared/contracts/` 中有版本的契约完成。
- 单据模块到装箱模块的数据传递，采用装箱模块公开的货物/柜型接口；不直接读写装箱模块数据库、状态或算法实现。
- 模块接口变更先更新契约，再更新调用方和契约验证；不得要求修改者先检查或补完其他模块内部实现。
- 需要跨模块变更时，变更范围必须限于接口契约、被授权的调用适配层及相关验证；其余实现仍由各自模块负责。

## 5. 接口规划

接口文档放在 `docs/interfaces/`，机器可读定义放在 `shared/contracts/`。每个接口文档说明：用途、所有者、输入、输出、错误、版本兼容策略、调用方向和最小契约验证。

首批接口：

1. `web-app-module-interface.md`：载体如何注册、导航和调用模块。
2. `trade-document-record.md`：单据提取的标准化业务记录，字段需包含值、来源文件/位置、提取状态和用户确认状态。
3. `container-planner-api.md`：装箱模块接收的柜型、货物尺寸/重量/数量及约束，以及返回的摆放结果和未装入项。
4. `document-export.md`：按输出模板生成文件时的格式、字段映射、校验错误和下载结果。

接口先定义稳定的业务含义，再选具体传输形式。当前应用是本机网页与本地服务，首选本地 HTTP/JSON 契约；如源码盘点发现模块在同一进程内调用更合适，可使用同一数据契约的函数适配器，不改变模块边界。

## 6. 规则文件和项目管理

### `AGENTS.md` 分层

- 根 `AGENTS.md` 控制所有贡献者：读相关 README/接口，选择单一模块边界，禁止跨模块查看或修改内部实现，跨模块通过契约协作；明确禁止把客户原始资料当作默认测试样例。
- `web-app/AGENTS.md` 只写载体代码、导航、装配和启动规则。
- 每个 `features/<feature>/AGENTS.md` 只写本模块内部约束、验证入口和公开接口位置。
- 子规则只补充父规则，不复制整份根规则；详细实现说明放模块 README/docs，不把 AGENTS 写成教程。

### 分类、命名和文件摆放

- 代码目录和接口 ID 使用简洁英文 kebab-case；已有中文资料目录先保持原名，避免无关搬迁。
- 源码按职责放入 `frontend/`、`backend/`、`tests/`；产品行为和接口说明放入模块 `docs/`；用户可见说明放 README。
- 样例按 `input/`、`templates/`、`expected/` 分类，名称注明格式与用途；样例不得混放在源码目录。
- 自动化测试与对应模块同目录；跨模块及便携包验收放根 `tests/`。
- 构建脚本、依赖锁定和打包配置放 `packaging/`；生成的可执行文件放 `发布包/`，不提交到源码目录充当实现。
- 日期型记录采用 `YYYY-MM-DD`；接口采用 `feature.resource.v1` 风格版本 ID；避免含义不清的 `misc`、`new`、`final2` 等名称。

### 单功能工作流程

1. 阅读根 `AGENTS.md`，再只读目标模块的 `AGENTS.md`、README 与相关接口。
2. 修改仅限目标模块目录；跨模块需求通过契约提出，不查看或直接改动其他模块内部实现。
3. 为目标模块新增/更新契约验证和模块内验证；只有改动载体或集成契约时，才运行相关集成/打包验收。
4. 更新本模块文档和变更记录；交付说明列明改动路径、接口变化和实际验证结果。

## 7. 迁移和交付阶段

1. **治理文档**：建立根 README/AGENTS、架构与项目管理文档、接口索引和模块规则。
2. **源码盘点**：确定 `ContainerPlanner.exe` 的构建入口、源文件位置、静态资源生成方式和依赖锁定方式；记录无法恢复的部分，不假设打包目录等于源码。
3. **载体与集装箱模块分离**：保持现有 UI 和计算行为，通过回归验证后，将载体启动和集装箱业务按责任边界迁移。
4. **单据功能实现**：从用户提供的输入样例及 INV/PL 模板建立映射、提取/核对界面、生成能力和模块样例测试；样例数据须获准并脱敏。
5. **便携打包**：将网页载体、两个模块、依赖、模板和静态资源一起打进可复制发布目录；在干净 Windows 环境验证解压、双击、打开网页、导入/导出和本机文件处理。

## 8. 验收标准

- 新参与者从根 README 能理解项目用途、双击启动方式、模块索引和当前源码状态。
- 根及模块 `AGENTS.md` 简短、分层且明确禁止越界查看/修改；模块公开接口足以让调用方工作。
- 集装箱模块和单据模块是网页中的并列入口；单据模块通过契约使用装箱能力。
- 单据样例、模板、预期结果分区存放，真实业务文件不会被无意复制进样例或发布包。
- 有可复现的构建说明和便携验收流程；新电脑不需另装开发环境即可运行发布版。
- 在源码盘点完成前，不宣称已经完成模块拆分或可从当前 exe 完整重建应用。

## 9. 不在本设计范围

- 本轮不实现单据字段提取、合同解析、INV/PL 填充、PDF 转换或业务计算。
- 本轮不修改当前网页、打包程序、真实业务文件或发布压缩包。
- 本轮不决定具体 OCR/解析依赖，须以用户实际样例、版式和便携打包验证结果为依据。
- 本轮不把当前本机应用改成云端服务，也不引入外部账号或云存储。
